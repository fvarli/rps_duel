Game engine spec

Pure Dart. Tested in isolation. Imported by duelController. No Flutter, no async, no I/O.

Resolution

// lib/domain/rps_engine.dart

class RpsEngine {
  const RpsEngine();

  /// What beats what.
  static const Map<MoveChoice, MoveChoice> _beats = {
    MoveChoice.rock:     MoveChoice.scissors,
    MoveChoice.scissors: MoveChoice.paper,
    MoveChoice.paper:    MoveChoice.rock,
  };

  RoundOutcome resolve(MoveChoice you, MoveChoice cpu) {
    if (you == cpu) return RoundOutcome.tie;
    return _beats[you] == cpu ? RoundOutcome.win : RoundOutcome.loss;
  }

  /// CPU move. MVP only uses .normal; rng + difficulty stub is in place
  /// so we can swap it for adaptive AI in a later phase without touching
  /// the duel controller.
  MoveChoice cpuMove({
    required CpuDifficulty difficulty,
    required List<MoveChoice> recentPlayerMoves,  // last 5
    Random? rng,
  }) {
    final r = rng ?? Random();
    switch (difficulty) {
      case CpuDifficulty.easy:
        // pure random
        return MoveChoice.values[r.nextInt(3)];
      case CpuDifficulty.normal:
        // random, but never repeat exactly the last cpu move twice
        return MoveChoice.values[r.nextInt(3)];
      case CpuDifficulty.hard:
        // Phase 2+ stub — counters the player's most-used recent move
        return MoveChoice.values[r.nextInt(3)];
    }
  }
}

Streak rules

  • Win while currentStreak ≥ 0 → currentStreak + 1.
  • Win while currentStreak < 0 → currentStreak = 1 (broken loss-streak).
  • Loss while currentStreak > 0 → currentStreak = -1.
  • Loss while currentStreak ≤ 0 → currentStreak - 1.
  • Tie → currentStreak unchanged.
  • bestStreak = max(bestStreak, currentStreak) after every round.
  • Reset Match zeroes both.

Round → side effects

  1. Engine resolves outcome.
  2. duelController creates a RoundRecord and pushes to historyRepository.
  3. statsController recomputes from stream (cheap — derived).
  4. achievementsController evaluates each achievement's trigger predicate; persists newly-unlocked.
  5. dailyMissionProvider increments progress if the round matches the mission template.
  6. analytics.roundCompleted(record) fires.

Pass-and-play behaviour

  • Same FSM. The "CPU" move is the second player's input — collected after the first player commits and looks away.
  • UI sequence: P1 picks → hide-away screen ("Pass to Player 2") → P2 picks → reveal.
  • RoundRecord still uses you / cpu field names — but the JSON contains mode: 'passAndPlay' so we know.

History persistence timing

  • Write on reveal → ready transition (i.e. after the player sees the verdict, before they tap again). Fire-and-forget; UI does not block.
  • If write fails (disk full, very rare), the round is dropped and we log to analytics. Never block the next round on persistence.
  • History is capped at 100 rows. Inserting the 101st evicts the oldest in the same transaction.

Haptics & sound implementation

One service per surface. Every call goes through the service so disabling them in settings is a single boolean flip.

HapticsService

class HapticsService {
  final SettingsRef _settings;
  HapticsService(this._settings);

  void tap()     => _fire(() => HapticFeedback.lightImpact());
  void lock()    => _fire(() => HapticFeedback.mediumImpact());
  void reveal()  => _fire(() => HapticFeedback.selectionClick());
  void win()     async {
    if (!_enabled) return;
    await HapticFeedback.heavyImpact();
    await Future.delayed(Duration(milliseconds: 80));
    await HapticFeedback.lightImpact();
  }
  void lose()  => _fire(() => HapticFeedback.heavyImpact());
  void tie()   async {
    if (!_enabled) return;
    await HapticFeedback.lightImpact();
    await Future.delayed(Duration(milliseconds: 120));
    await HapticFeedback.lightImpact();
  }
  void error() => _fire(() => HapticFeedback.heavyImpact());

  bool get _enabled => _settings.read().hapticsOn;
  void _fire(VoidCallback fn) { if (_enabled) fn(); }
}

Safe no-op fallback: if the platform doesn't support a given haptic (older Androids), the call returns silently. HapticFeedback APIs are platform-aware.

SoundService

Plugin: audioplayers 6.x with a single shared AudioPool per theme. Pool warmup happens during Splash so the first play() is < 16ms.

class SoundService {
  final SettingsRef _settings;
  final ThemePackRef _theme;
  AudioPool? _pool;

  Future<void> warmupForPack(ThemePack pack) async { ... }

  void play(SoundEventId id) {
    if (!_settings.read().soundOn) return;
    final assetPath = _theme.read().sounds.assetFor(id);
    _pool?.play(assetPath);
  }
}

enum SoundEventId {
  uiTap, lock, shuffleLoop, reveal, win, lose, tie,
  achievement, reward, purchase, error,
}

Settings toggle behaviour

  • Toggling "Sound" off cancels any in-flight loops (e.g. shuffle) immediately.
  • Toggling "Haptics" off has no in-flight cleanup; just blocks new calls.
  • If iOS / Android system "Reduce haptics" is on, we respect it — system overrides app.

Frequency rules (enforced in adsController)

  • No interstitial in the first 5 minutes of first session.
  • No interstitial during onboarding or theme select.
  • No interstitial during active duel — only between matches.
  • Frequency cap: 1 per 4 rounds, minimum 90s between any two interstitials.
  • Players with adsRemoved == true: zero interstitials, ever. Rewarded ads remain available.
  • If ad fails to load > 3× in a row, back off for 10 minutes.

Engineering guardrails

Rules for Claude CLI. Violations get reverted. These are the things that will tempt anyone shipping fast — they're written down so we don't have to argue at PR review.

Hard rules

  1. Do not overengineer. If a one-file solution exists, ship it. Defer abstractions until the second use.
  2. Do not build a backend in MVP. No HTTP. No Firestore reads. No Cloud Functions. Local Isar only.
  3. Do not implement realtime multiplayer. The schemas are PvP-shaped; the network code is not in this phase.
  4. Do not add login or account creation. Device-scoped anonymous play only. No SSO, no Apple Sign-in, no email/password.
  5. Keep the game engine pure Dart. Zero flutter imports in lib/domain/. If you can't unit test it without a widget, it doesn't belong there.
  6. Keep the theme system runtime-swappable. No const Material themes. No hardcoded colours in widgets. Every visual constant flows from ThemePack.
  7. Localization from day one. No raw strings in widgets — always go through generated l10n. CI fails if a hardcoded string is detected.
  8. Preserve compile health. Every commit passes flutter analyze. No // ignore: ... blanket disables.
  9. Run analyze + test after each phase. If a phase is described as "done" without proof of green analyze/test, it isn't done.
  10. Small commits. One phase per commit. No "WIP" or squash-prevention. Each commit is buildable and runnable on its own.

Soft rules

  • Prefer composition over inheritance for widgets. The only abstract class we use is ThemePack; everything else is composed.
  • One controller, one responsibility. If you find yourself reaching across providers in a notifier, the boundary is wrong.
  • SVGs over PNGs for all icons. PNGs only for raster art (App Store screenshots, splash logo if needed).
  • No dependency upgrades mid-phase. Lock pubspec.lock and only bump in dedicated dependency-update PRs.
  • Comments explain why, not what. The code says what. If a comment restates a variable name, delete it.

Anti-patterns to refuse on sight

  • Banners ads in MVP. Refused.
  • Cloud Firestore "to be safe". Refused.
  • "Just one quick state-management library swap". Refused.
  • Custom painters for the picker or duel stage. Refused (use composition).
  • String concatenation for localized copy. Refused (use ICU).
  • Ads during onboarding, first-session, or any duel phase. Refused.
  • Login screen "even just as a stub". Refused — anonymous device-id is the contract.
If in doubt, leave it outThe point of the scope lock in §01 is that anything not listed is a "no". A great feature outside the scope of MVP is still a "no". Write it down for Phase 2 and move on.
