# Play Store closed-test plan

> Plan for the v1.0.x closed-testing window that precedes the production-access application. Owner: operator.

## Track and policy context

- **Track:** Play Console → Testing → Closed testing → first closed-test track.
- **Why a closed test (not internal):** Google Play requires new personal-developer-account apps to complete a 14-day closed test with at least 12 opted-in testers before being eligible for production access (policy effective late-2023 onward). Internal testing alone does not satisfy this.
- **Duration:** 14 calendar days minimum, measured from the moment the first eligible tester opts in via the testing link. Plan for 16 days of slack so a late opt-in doesn't reset the clock.

## Tester pool

- **Target size:** at least 12 unique opted-in testers (Play Console requirement). Operator should aim for 15–20 to absorb dropouts.
- **Recruitment channels:** personal network first; if short, supplement via a small ad placement or a relevant Discord/Reddit community for casual mobile games. Each tester must accept the email invite and install via the Play Store testing link (sideloads do not count toward the policy minimum).
- **Tester device mix (target):** at least one device on each of API 26 (Android 8), API 30 (Android 11), API 34 (Android 14), API 35 (Android 15). At least one device with a display cutout (notch / hole-punch). At least one 10-inch tablet if reachable.

## Devices to cover

| Surface | Minimum coverage | Why |
|---|---|---|
| Phone, API 26 | one tester | The app's minSdk floor. Confirms haptic feedback + safe area work on older Android. |
| Phone, API 34/35 | two testers | Most users will land here over time; predictive-back + edge-to-edge gestures most likely to surface bugs. |
| Phone with notch / hole-punch | one tester | Confirms `SafeArea` actually keeps content out of cutouts on real hardware. |
| Tablet (any) | one tester if reachable | Confirms `ConstrainedBox(maxWidth: 460)` produces an acceptable centered layout rather than stretched buttons. |
| RTL / non-English locale | one tester (or operator) | Tests Spanish + Turkish UI strings under longer translations. Already covered by automated widget tests, but a human read-through is worth doing once. |

## Test scripts

The operator should send these to testers along with the testing link. Each script is short by design; total commitment per tester is < 10 minutes.

### Script A — first-run smoke

1. Install via the testing link, accept the tester invite.
2. Open the app. Confirm the title bar reads "RPS Duel" and the prompt below it reads "Choose your move."
3. Tap **Rock**. Wait for the reveal. Confirm a brief haptic on tap, and a stronger haptic when the result appears.
4. Tap **Next Round**. Confirm the Reset Game button below it does not jump.
5. Play four more rounds with a mix of Rock / Paper / Scissors. Confirm the score row updates and the history list grows.

### Script B — settings + localization

1. Tap the gear icon in the top right.
2. Open **Language**. Switch to **Türkçe**. Confirm the screen retitles itself ("Hamleni seç" appears under the score row). Switch back to English.
3. Open **Difficulty**. Set to **Easy**. Close. Reopen settings — confirm Difficulty subtitle reads "Easy."
4. Open **About RPS Duel**. Read the dialog. Close.

### Script C — persistence

1. Play three rounds.
2. Force-stop the app from Android Settings → Apps.
3. Reopen the app. Confirm scores, history, current/best streak, and difficulty all survive.
4. Open settings → **Reset data** → confirm. Confirm scores zero out but unlocked achievements stay.

### Script D — daily challenge

1. Play three rounds choosing **Scissors** in each. Win at least one of them.
2. Confirm the Daily Challenge card progresses (0/3 → 1/3 → ...).

## Success criteria

The closed test is successful if **all** of the following are true at the end of the 14-day window:

- At least 12 unique opt-ins reached and held to the end of the window.
- Zero ANRs (application-not-responding events) in Play Console Vitals.
- Zero crashes attributed to the production-release build in Vitals; or, if any appear, all are root-caused with a fix in a subsequent closed-test build.
- Every tester-reported item is logged in `closed_test_feedback_backlog.md` with a triage decision.
- No outstanding **Blocking** or **Major** items in the backlog.
- The Pre-launch report (auto-generated by Play Console after each upload) shows no policy or compatibility issues.

## Exit checklist

Before clicking "Apply for production access" the operator confirms:

- [ ] All success criteria above are met.
- [ ] `production_access_answers_draft.md` has been filled in with truthful answers (no placeholders left).
- [ ] `release_notes.md` accurately describes what shipped in the most recent build promoted toward production.
- [ ] Privacy policy is publicly hosted at the URL listed in the Play Console Data Safety form.
- [ ] App's `versionCode` is the highest yet uploaded to the testing track.

## Risks / mitigations

| Risk | Mitigation |
|---|---|
| Fewer than 12 testers opt in by day 14 | Recruit early. Send the testing link week one with a reply-by-date. Have a small backup pool of 5+ on standby. |
| A blocking bug surfaces day 12 | Build is rejected for production application; ship a fix as a new closed-test build, restart the 14-day clock only if Play Console requires it (current policy: significant changes may reset). |
| Tester feedback is sparse / low quality | Use Script A–D above; ask follow-up questions on free-form responses. Don't accept "looks good" without a confirmed scripted run. |
